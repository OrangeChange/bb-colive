# 大航海动作字段与渲染规则

> 本文的本地日志路径是历史样本证据，不是当前运行日志目录的格式。当前运行时完整协议内容由 `source-*` 诊断流保存，旧 `conn-*` 仅用于追溯；当前产品边界见[项目状态](../project-status.md)。

## 结论

`USER_TOAST_MSG_V2` 的 `guard_info.op_type` 不能单独作为“开通 / 续费 / 升级”的显示依据。
当前本地样本中，`op_type=1` 同时出现了“开通”和“续费”，因此界面应优先显示服务端
`toast_msg` 原文中的动作词；`op_type` 继续保留，供后续核对和研究使用。

当前适配规则：

1. 从 `toast_msg` 提取“开通、续费、升级、降级”。
2. 渲染优先使用提取结果；“升级 / 降级”显示为“升级为 / 降级为”并接目标大航海等级。
3. 没有 `toast_msg` 时，才使用 `op_type` 兜底：`2=续费`、`3=升级为`、`1=开通`；未知值显示“上舰”，不强行断言。

线上 `guard_level` 的等级方向为 `1=总督、2=提督、3=舰长`；应用模型已转换为
`1=舰长、2=提督、3=总督`。两条反例都显示：用户在购买前已存在大航海状态，且本次

“续费了提督，今天是TA陪伴主播的第1天”。Laplace 的本地前端解析同样直接从文案提取
“开通 / 续费”，而不是使用 `op_type`。

## 后续验证

继续收集以下成对样本，再判断 `op_type` 的正式含义：同等级续费、跨等级购买、明确升级、
大航海到期后重新购买，以及同一用户不同月份的重复购买。现阶段不根据 `op_type=1` 擅自改写
服务端动作，也不把“第 1 天”当作“开通”的充分条件。

## 大航海红包／登船活动：暂不匹配

需要将“大航海红包领取后上舰”和普通大航海购买区分开。历史协议资料中，
`GUARD_LOTTERY_START` 被描述为“房间内登船活动开启消息”；旧命令 `LOTTERY_START` 在
`type=guard` 时也属于登船活动。其 `lottery.thank_text` 可以是“恭喜某用户上任舰长”，
这只证明该文案用于历史登船活动开始通知，不能证明它是所有大航海红包的发送或结果文案。

目前没有当前直播间的真实原始报文来确认：

- 大航海红包实际使用的命令名和字段；
- 发起、领取、上舰、开奖之间是否分别产生事件；
- 领取后的按天大航海是否带有可识别的红包来源标记；
- 是否存在独立的结果事件。

因此，当前 `GuardBuy.guard.unit` 为“天”只能作为临时的低价大航海筛选条件，不能作为
“来自大航海红包”的协议级判断。获得真实样本前，不新增大航海红包解析分支，也不改变
普通红包和 `GuardBuy` 的现有分类、渲染与播报模板。

## 当前渲染记录（2026-09-05）

- 大航海购买行中的用户名、动作、等级、`×N天` 和金额使用同一高度的行内居中盒，避免
  金额或时长相对身份标签下沉；陪伴天数仍作为较弱的辅助信息显示。
- 该规则只约束布局，不改变服务端动作文案。`开通 / 续费 / 升级 / 降级` 仍按前文的
  `toast_msg` 优先规则渲染。
