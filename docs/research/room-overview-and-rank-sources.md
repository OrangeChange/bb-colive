# 直播间概览与榜单数据来源调查

> 2026-09-04 · 页面观察、B 站官方规则及前端源码、公开接口实测、本地协议资料交叉核对。
> 样本房间：6431492，主播“符瑶koritsu”，主播 UID 2109776。
> 2026-09-04 已据此实现第一版概览与榜单；本文保留接口实测、交互核验和已知边界。数值是请求时快照，不是固定值。

## 一、产品目标与调查结论

- 概览数据放现场底栏左侧，不做趋势图，包含直播时长。
- 用户最终确认观众数量以B站直播间显示为准，不接受人气值、累计看过或名单长度替代。界面标注“观众”。
- 贡献榜：前三头像，悬停展开列表，显示贡献值而不是金额。
- 大航海：只做总榜（网页“陪伴榜”），前三头像，展开完整名单和陪伴天数。
- 两个榜单放在当前概览数据的位置。

| 目标 | 已有依据 | 当前结论 |
|---|---|---|
| 主播信息、标题、分区、看过、点赞、勋章及大航海人数 | 页面初始数据已有对应字段 | 可获取 |
| 直播时长 | 页面开播时间戳及视频区域显示 | 可据开播时间计算 |
| 与B站页面口径一致的观众数量 | 页面新旧榜分支及计数文本、贡献榜HTTP快照、ONLINE_RANK_COUNT | 已接入对应快照与推送，不把计数解释为所有匿名观看者总量 |
| 贡献榜前三及列表 | queryContributionRank 实测成功 | 按用户确认的范围展示最多前100名 |
| 大航海陪伴总榜 | topListNew 全8页实测 | 当前房间162名完整取得，含陪伴天数 |

此前“online_count 已确认是真实在线人数”“贡献榜可分页取得全部用户”“陪伴榜接口尚未确定”三项结论已由本次证据修正。字段存在、字段名称、统计口径、名单覆盖范围分别记录，不再互相替代证明。

## 二、概览字段

页面 SSR 的 roomInfoRes.data 已观察到下列字段：

| 目标 | 字段 | 含义／使用边界 |
|---|---|---|

| 人气 | popularity.popularity、popularity_text | 本次页面 room_info.online 对应的也是人气，不得改名在线人数 |
| 看过 | watched_show.num | 累计看过，不是当前在线 |
| 点赞 | like_info_v3.total_likes | 点赞累计快照 |
| 勋章名称、粉丝团人数 | anchor_info.medal_info.medal_name、fansclub | 不等同主播账号总粉丝数 |
| 大航海人数 | guard_info.count | 本次为162 |
| 贡献榜初始条目 | room_rank_info.user_rank_entry.user_contribution_rank_entry.item | 初始前三或前七，非完整榜单 |

直播时长可按“当前时间－开播时间”计算，不需要逐秒请求。后续实现须区分未直播、下播与断连：网络断连本身不能视为下播。下播后的停止时间以直播状态／结束事件为依据。

## 三、在线人数：确认到哪一步

### 1. 已确认的来源关系

WebSocket 的 ONLINE_RANK_COUNT 包含 count、online_count 及对应文本字段；它们不是页面 SSR 字段。

当前 B 站网页主脚本的 ONLINE_RANK_COUNT 处理函数按 isShowNewRank 分支选择 online_count_text 或 count_text，再更新 onlineGoldCount。可以确认新旧榜使用不同计数显示，不能仅凭 online 一词证明其中任一值是全部实际观看者总量。

历史原始日志 conn-1700301235-20260903-190511.ndjson 中有4402条该命令，154条 count 与 online_count 不同，例如88/98、91/99、92/100。这证明两字段不是重复别名，不证明 online_count 的完整覆盖口径。

以下值不能作为目标在线人数：

- WebSocket 心跳回复（操作码3）：协议为人气值。@laplace.live/ws 的 online 属性名称不能改变该语义。
- WATCHED_CHANGE.data.num：累计看过。
- ONLINE_RANK_V3 列表长度：榜单条目数量，不是全房间人数。

### 2. 官方规则的关键限制

当前页面贡献榜规则链接指向 B 站“在线观众”规则页；该页 test_type=b 使用官方文档3008。

规则内容说明：

- 当前在线用户按贡献值排序；点赞、弹幕和送礼都可能贡献分值。
- 离开或重新进入直播间会改变榜单信息。
- 一部分实际观看者因未登录、未绑定账号、内容安全或技术限制，不能出现在在线观众榜中。

因此，完整榜单也不等于全部观看者名单。规则没有明确写明 online_count 是否另行计入不能展示的观众，不能把“名单排除这些人”直接升级为“计数字段一定排除这些人”，也不能反向保证计数包含他们。

结论：已确认它是平台在线榜计数，尚不足以承诺覆盖全部实际观看者。用户随后明确接受“与直播间显示一致”的口径，当前实施以此为准。

### 3. 上限与缺失不能混为一谈

备份社区文档把 count 记为高能用户数量、online_count 记为在线用户数量，并注明存在上限；没有给出上限数字或适用条件。本地 @laplace.live/internal 的类型注释则称其为旧／新版高能榜，并将 online_count 标为可选字段。

- 贡献榜“列表最多100名”已由官方接口响应确认。
- 数值计数是否封顶、具体上限是多少，尚未证实。
- 历史日志出现过 online_count=91991；不能把100人的名单上限当成计数上限。
- 缺少 online_count 时不能自动拿 count 当作同一口径，也不能把缺失变成0。

### 4. 另一个尚未验证的路径

公开项目 xuan25/BiliOnlineRank 区分在线用户接口 getOnlineRank 与高能榜接口 getAnchorOnlineGoldRank，前者响应模型含 onlineNum。

该项目 README 要求官方客户端 Access token；调用代码使用 platform=pc_link 及登录态。此次无登录态读取 getOnlineRank 返回 -101“账号未登录”。

这提供了客户端／主播侧接口线索，但尚未验证：
- 当前网页登录态是否足够；
- 是否仅允许主播读取自己的房间；
- onlineNum 是否包含匿名观众，是否等于当前直播业务要求的真实在线。

未提取账号令牌、未修改登录权限。下一步若要走该路径，应在用户明确提供的主播侧可用环境中对照官方客户端数据，不能以旧项目名称证明今天的统计口径。

### 5. 应用接入

src/protocol/adapter.ts 已移除 online_count ?? count；分别保存新旧榜计数、对应文本和接收时间。概览按榜单配置选择对应分支；HTTP快照与后续WS推送按更新时间取值。

优先使用平台计数文本（如“1.2万”），缺失文本时显示原始整数；数字缺失显示“—”，数字0照常显示。不会把心跳人气映射到观众数量。

## 四、贡献榜：接口已验证，但不是无限分页

接口：

```text
GET https://api.live.bilibili.com/xlive/general-interface/v1/rank/queryContributionRank
ruid=2109776
room_id=6431492
type=online_rank
switch=contribution_rank
platform=web
page=1
page_size=100
```

本地 JLiverTool、jlivertool-repo、bili-live-hime 均有参考调用。本次额外进行了实际请求，不再依据“参数名叫page”判断分页有效。

| 请求 | 返回条数／排名 | 观察 |
|---|---|---|
| page=1，page_size=50 | 50条，1—50 | 请求成功 |
| page=2，page_size=50 | 仍为1—50 | 未取得后50名 |
| page=1，page_size=100 | 100条，1—100 | count快照397 |
| page=2，page_size=100 | 仍为1—100 | count快照397 |

响应 list_end_prompt 明确提示“最多展示100名观众”；config.value_text 为“贡献值”。count 大于 item.length 不表示还有可正常翻页取得的名单。

前三可从 item 前三提取。用户信息在 uinfo，分值在 score，排名在 rank。部分用户分值为0，不应自行剔除或将名单误认为只有付费用户。

用户已确认贡献榜只需平台允许展示的前100名，不要求取得计数中的全部用户。实现只请求page=1、page_size=100，不提供无效的翻页操作。

本次公开请求未附带 Cookie 或 WBI 签名也返回 code=0；因此不能说此接口必需WBI。具体请求仍沿用应用现有HTTP能力，不能由单房样本推断所有接口都免鉴权。

## 五、大航海陪伴总榜：接口和完整性已验证

接口：

```text
GET https://api.live.bilibili.com/xlive/app-room/v2/guardTab/topListNew
roomid=6431492
ruid=2109776
page=1
page_size=20
typ=0
platform=web
```

本地 @laplace.live/internal 提供该接口类型线索。返回字段：

| 字段 | 含义／实测 |
|---|---|
| data.info.num | 总人数162 |
| data.info.page | 总页数8，不是当前页 |
| data.info.now | 当前页 |
| data.top3 | 前三，每页重复携带 |
| data.list | 当前页其余用户 |
| rank | 官方排名 |
| accompany | 页面对应的陪伴天数 |
| uinfo.uid | 用户UID |
| uinfo.base.name、face | 用户名和头像 |
| uinfo.guard.level | 大航海等级 |
| uinfo.medal | 勋章名、等级及配色 |

前三与此前网页“陪伴榜”观察一致：

| 排名 | 用户 | 陪伴天数 |
|---|---|---|
| 1 | 美波p | 306 |
| 2 | 虚神耀月 | 1937 |
| 3 | 北兰爱丽丝 | 1525 |

完整请求第1—8页：list条数依次20、20、20、20、20、20、20、19；top3仅计一次，合计162条、162个不同UID，与info.num一致。页2延续到排名24，末页到162；越界页9的list为空。

所以此接口在当前房间能实现完整总榜，而不是只取前三或首页。未附带Cookie／签名的本次公开请求成功。

亲密度与陪伴天数是两种独立排序。`accompany`只表示陪伴天数，不能当成亲密度。界面默认使用亲密度，可切换到陪伴天数；两种方式均使用服务端返回的顺序及`rank`，不在本地重排分页或重算名次。

2026-09-04在24326872（UID 65970249）直接请求验证：`typ=0`保持原亲密度顺序，前三为南羽捞月（7天）、青東客_（23天）、史卡蕾特（23天）；`typ=1`切换为陪伴天数顺序，前三为青東客_、史卡蕾特、卷卷羊咩咩_（均23天）。随后读取`typ=1`全部5页，87条、87个不同UID，陪伴天数从23到1，跨页无逆序。人数在验证期间由86增长至87，属于不同时间快照。亲密度具体计算公式没有由该接口确认。

旧版topList在部分本地模型中也有accompany；另一个参考模型未声明该字段，不证明服务端不返回。当前采用已实测匹配页面的新接口作为依据。

## 六、已实现行为

- 概览通过现有登录态及WBI签名请求getInfoByRoom；未签名请求曾返回-352，应用内签名请求已成功。基础字段初次加载，连接期间每60秒刷新；连接状态及开播/下播推送触发刷新。
- 看过、点赞、粉丝团采用较新的HTTP或WS同字段快照；旧房间缓存不会一直压住重连后的新快照。
- 直播时长每秒在本地计算，无每秒网络请求；收到下播事件后冻结，收到新场次开播后重新计时。未知开播时间或未捕获准确结束时刻的离线场次显示“—”。断连不是下播。
- 观众榜（数据源仍是贡献值接口）是动态快照：连接期间收起时每30秒、展开时每10秒刷新；展开时距上次更新满10秒则立即刷新，正在请求时不重复触发。不按送礼金额重建贡献值。平台接口已验证最多提供前100名，因此只读取并展示这100名，不伪造第101页。列表统一使用可滚动榜单容器；观众榜到达底部时不会发出无效分页请求。
- 大航海初次加载前三与第一页，继续向下滚动到列表底部时自动加载余下各页；前三只拼一次，按UID去除跨页重复，保留服务端名次。亲密度`typ=0`与陪伴天数`typ=1`分别缓存第一页和后续分页，切换时取消旧排序在途请求并回到列表顶部。收起且连接中每60秒刷新第一页；展开阅读期间不自动替换已加载的分页。手动刷新后重新开始分页。分页失败会停止自动触发，列表底部提供“重试加载”恢复入口。
- 超过100人的大航海名单使用虚拟滚动；实测跨100名加载时滚动位置保持不变。
- 缓存按实际连接的真实房间号隔离，不使用最后使用主播兜底发起请求。只有WS状态为connected且存在登录态时允许初次请求、轮询、手动刷新和分页；connecting/reconnecting/closed/error/idle期间停止更新。断开、切换房间和卸载时显式取消在途请求。断开后可以展开已缓存的榜单，不能刷新或加载更多；已加载分页保留。启动未连接且无快照时显示占位，不主动读取概览。
- 时长按房间保存最后观测时刻：连接期间递进，断开/重连等待期间冻结；重新连接后依据本场实际开播时间恢复。主播下播但WS仍连接时，使用下播事件冻结时长，不等同于断开。暂停时概览及榜单显示“未连接 · 数据已暂停”。
- 榜单支持悬停、点击和键盘展开；Escape、外部点击及非固定展开时移开鼠标可关闭，相邻榜单的延迟关闭互不影响。展开标题分别为“观众榜”和“大航海”，已显示人数放在标题同行，右侧保留刷新按钮，移除叉号。前三头像通过共用`RankTopThree`组件按UID跟踪：名次上升向左、下降向右，新入榜从右侧进入、离榜向右退出；系统减少动态效果时直接更新位置。
- 失败时保留已成功的缓存并提供重试；名单有加载中、空榜、分页失败状态。HTTP榜单不作为事件写入原始消息和UI事件日志。
- 这些刷新间隔是本应用的实现策略，不是B站网页内部机制。

实现入口：`src/protocol/roomInsights.ts`、`roomInsightsApi.ts`、`src/hooks/useRoomInsights.tsx`、`src/components/RoomRankings.tsx`、`RoomOverviewBar.tsx`。共享Context独立于可热更新的组件，避免开发模式替换组件时产生Context实例不一致。

### 本轮验证

- 应用内真实接口：31999413概览成功，大航海107人完整加载；6431492正在直播，概览开播时间及贡献榜前100名读取成功。

- 单元测试覆盖零值/缺失值、贡献值、身份映射、分页前三去重、HTTP/WS更新顺序、下播冻结与重新开播。

已知限制集中如下：
- 全部实际观看者的计数口径和取得方式仍未验证；不以人气、累计看过或榜单长度替代。
- 贡献榜当前公开路径最多展示100名；列表上限与人数计数上限不同。

- 登录态、灰度配置、开播状态可能改变返回内容；本次实测不证明接口长期稳定性。
- 断连期间不能接收下播推送；重新取得状态前只保留已知数据，不能保证获知准确结束时刻。
- 本轮内置浏览器标签读取超时，未完成实现后与B站页面同一时刻数值的逐项对照；依据为此前页面调查与本轮官方接口实测。
