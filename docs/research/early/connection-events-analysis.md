# B 站直播连麦事件采集与分析档案

> 早期调查证据，不作为当前功能规范。


> 建档时间：2026-09-06。
> 目的：持续收集普通语音/视频连麦、多人连线以及承载在连麦上的 PK 活动，逐步还原命令归类、
> 字段含义和完整运行逻辑。当前数据不完整，本文明确区分真机证据、参考资料与待验证假设，
> 不因命令名或单次快照提前固化状态枚举。

## 一、与 PK 的关系

连麦和 PK 不是互斥分类：

- **连麦会话**描述谁与谁建立实时音视频连接、成员如何变化、会话何时开始和结束。
- **PK 玩法**描述连麦会话上的邀请、开战、比分、胜负和惩罚。
- 普通连麦可以完全没有 PK；一场视频 PK 则可能同时产生通用连麦快照与 `PK_BATTLE_*`。

因此数据层应分别保存“连麦会话”和“PK 玩法”，再通过会话标识与时间范围关联，不能把
`UNIVERSAL_EVENT_GIFT(_V2)` 直接归成 PK，也不能看到 `VOICE_JOIN_*` 就判定已经连上用户。

## 三、不能混淆的判断

### 1. 开放连麦不等于实际连麦

只出现 `VOICE_JOIN_SWITCH(_V2)`、`VOICE_JOIN_LIST` 或
`VOICE_JOIN_ROOM_COUNT_INFO` 时，只能记录“连麦能力/申请队列状态变化”。至少需要成员、
频道或明确的会话生命周期证据，才能建立连麦会话。

### 2. 连麦不等于 PK

只有出现 `PK_BATTLE_*`、`PK_INFO` 或经实例确认的同族命令时，才能给会话附加 PK 玩法。
`UNIVERSAL_EVENT_GIFT(_V2)` 自身只是通用多人连线状态，不能单独证明正在 PK。

### 3. UNIVERSAL_EVENT_GIFT 不是逐笔礼物

该命令可能携带 `multi_conn_info.scores[].price`，表示连线中各主播的累计贡献；它不包含
一笔送礼所需的发送者、礼物 id、数量等完整语义。逐笔礼物仍以 `SEND_GIFT(_V2)` 为准。

## 四、关联字段

| 字段 | 用途 | 当前限制 |
|---|---|---|
| `biz_session_id` | 关联多人连线快照与 `PK_INFO.pk_basic` | 已在一场 PK 中验证；普通连麦仍需验证稳定性 |
| `interact_channel_id` | 通用多人连线频道 | 只有参考样例，尚未验证生命周期内是否恒定 |
| `channel_id` | 一对一视频连线 START/MSG/END 关联 | 只有备份文档样例 |
| `members[].uid/room_id/link_id` | 识别连线成员、房间和席位连接 | 需验证成员加入、退出时的版本变化 |
| `session_status` / `room_status` | 候选状态机字段 | 枚举含义尚未通过完整流程确认 |
| `members_version` / `version` | 快照新旧与成员变化 | 是否严格单调仍待实测 |
| `start_at` / `join_time` / `current_time` | 建立邀请、成员加入及消息时间线 | 不同命令时间字段口径需交叉验证 |

## 六、后续采集目标

每次采集应覆盖活动开始前、完整运行期和结束后一小段时间，并优先寻找以下实例：

1. 主播打开/关闭连麦功能，确认 `room_status`、`root_status`、`conn_type` 的变化。
2. 观众申请、取消申请、主播接受/拒绝，确认 LIST/COUNT 是否只有状态还是另有用户列表命令。
3. 一对一语音或视频连线从邀请到结束，核对 `channel_id` 与双方房间是否一致。
4. 多人连线成员逐个加入、退出及席位调整，确认 `session_status`、`members_version` 和布局变化。
5. 普通连麦转为 PK、PK 结束后继续连麦，确认同一 `biz_session_id` 下两层生命周期的边界。
6. 主播或连接异常中断，确认是否有独立取消、超时、断线和恢复命令。

## 七、当前产品处理

- 原始连接日志在适配器之前记录，已知和未知连麦命令都会保留。
- 当前现场不渲染连麦与 PK 状态，避免在字段和生命周期未验证前产生误报。
- 后续每捕获一种完整活动，都应在本文补充：原始时间线、同源重复命令、字段变化、关联键、
  状态迁移和可展示信息；只有得到实例证据后才进入事件模型与渲染设计。
