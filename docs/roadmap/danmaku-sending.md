# 弹幕发送、回复与表情

状态：main 已接入，模拟请求及界面验证通过，真实发送待授权验收。日期：2026-11-26。

## 目标与范围

在现场以紧凑悬浮输入框完成普通文字发送、回复用户和直播表情发送，不改变现场排版、阅读位置、采集和档案写入。全部修改在 main 分支进行。

PiliPlus 是主要参考：[发送与表情接口](https://github.com/bggRGjQaUbCoE/PiliPlus/blob/main/lib/http/live.dart)、[表情面板](https://github.com/bggRGjQaUbCoE/PiliPlus/blob/main/lib/pages/live_emote/view.dart)。参考其协议调用与职责划分，用项目现有 TypeScript、Tauri HTTP、登录和 WBI 能力实现；不引入 Flutter、Python、机器人框架或新的连接。

常用语单独列为后续手动输入辅助。本轮不做回复提醒、定时发送、事件触发、自动回复、群发、自动拆分或付费互动。

## 方案选择

| 方案 | 取舍 |
| --- | --- |
| 安装完整第三方客户端／机器人发送库 | 重复已有登录和连接，增加运行依赖，不采用 |
| 用简单发送示例实现纯文字 | 改动少，但需另补回复和表情流程，不作为主要依据 |
| 按 PiliPlus 的完整发送流程适配现有请求层 | 保留现有架构，文字、回复与表情共用一条发送链路，推荐采用 |

PiliPlus 使用 GPL-3.0；本方案不直接移植其源码。后续若采用具体代码片段，先核对许可并同步第三方声明。参考入口和调查边界见[开发参考项目](../research/reference-projects.md)。

## 现场入口与悬浮框

- 在“弹幕”或“弹幕与互动”标题文字右侧紧邻放置 MessageCirclePlus 对话气泡加号图标，悬停及无障碍名称为“发送弹幕”。事件数和统计摘要仍在标题栏右侧。
- 双区及多区布局都只有弹幕所在分区提供入口；互动、收益分区不重复放按钮。切换布局不丢草稿。
- 点击后在标题下方打开悬浮框，宽度以 360px 为目标，受可用窗口宽度约束，自动避开屏幕边界。通过 portal 展示，不被事件列表的 overflow 裁切，也不挤压列表。
- 复用现有 shadcn／Radix Popover、Input／Textarea、Button、Tabs 和提示组件，保持软件配色、字体及焦点规范，不另造弹窗体系。
- 顶部显示目标主播；回复模式另有“回复 某某”及取消图标。输入区域下面仅放表情按钮、字数、发送按钮和必要状态。
- 打开后聚焦输入框；Enter 发送，Shift+Enter 换行。发送普通弹幕时将输入换行整理为空格，不自动拆成多条。中文输入法确认候选时不发送，选字期间 Esc 不关闭整个悬浮框。
- 点击外部、Esc 或再次点击入口可收起，焦点返回入口；从事件菜单打开时，菜单关闭后再聚焦输入框。
- 没有有效登录、没有已解析的目标房间或正在切房时，入口保留并提示原因，禁止发送。网络重连期间保留草稿；首版以连接就绪为发送条件，避免目标状态含糊。

## 回复联动

- 现有现场事件菜单增加“回复该用户”，使用 Reply 图标。已有有效用户 UID 且属于当前房间的事件才提供该操作，不限制为普通弹幕。
- 快捷菜单配置可添加 reply，沿用最多三项及现有排序；不自动更换用户当前选择，不改变默认三项。
- 回复动作打开同一个输入框并设置目标 UID、显示名称和来源房间，保留当前文字草稿。切换回复对象仅更新目标；取消回复转为普通发送。
- 使用平台 reply_mid，不仅在正文前拼接 @昵称。replay_dmid 只有在采集数据明确保留真实平台弹幕 ID 时才填写，否则按平台允许的空值发送。
- 当前 DanmakuEvent.id 可能是平台 ID，也可能是生成的去重键，不能直接据其外形推断为平台 dmid。首版先实现可靠的回复用户；不为消息引用改写整套事件身份或历史档案。
- 回看、收藏、OBS、外置预览和只读副窗口不增加发送入口；没有发送回调的菜单不出现 reply，也不影响其余动作。

## 表情

### 数据与权限

使用当前登录账号、真实房间号，读取 GetEmoticons 的 pc 表情包。只在打开表情选择器时加载；当前账号、当前房间范围内复用内存结果，提供失败重试和手动刷新。切换账号或房间后不沿用旧权限及表情选择。

模型保留包 ID、类型、名称、封面，以及表情 unique、文字、图片、原始宽高、可用权限和解锁说明。PiliPlus 的简化模型未包含表情权限，本项目必须保留这些字段，不把所有返回项都视为可发送。

### 选择与发送

- 表情按钮在输入框内展开分组网格，顶部或底部用包封面切换，窄窗口内可滚动；图片保持比例，不强制拉伸横幅。
- 普通文字型表情在光标位置插入图片，内部保留平台文本标记，允许与文字及回复组合。只有依据包类型和实际返回字段确认属于文字型时才走这条路径。
- 独立大表情使用 emoticon_unique 和 dm_type=1，点击即发送；文字和回复草稿保留。
- 独立表情直接发送，不删除文字与回复草稿；发送失败保留输入内容，由用户自行再次选择。
- 未解锁表情不可发送，悬停说明平台返回的条件；无权限说明时只显示“暂不可用”，不自行推断用户需要购买什么。
- 加载、空列表、请求失败和图片失败都有对应显示；表情失败不阻断普通文字发送。
- 回复与独立大表情的组合必须专项实测。PiliPlus 在独立表情分支中没有同时附带其文字回复参数，不能由普通文字支持回复推导表情也支持。回复模式点击独立大表情时直接单独发送，不显示确认提示，也不清除原回复对象。

## 请求与发送状态

### 最小请求层

新增 src/protocol/danmakuSending.ts，复用 api.ts 中的 BILI_HEADERS、encWbi、getNav、ApiError 及现有 Tauri HTTP 插件。

接口边界：

- getRoomEmoticonPackages(roomId: number, cookie: string, signal?: AbortSignal): Promise<RoomEmoticonPackage[]>：返回规范化表情包及权限。
- sendLiveDanmaku(request: LiveDanmakuRequest, session: Session, signal?: AbortSignal): Promise<LiveDanmakuSendResult>：Session 复用 protocol/login.ts；结果为 accepted 或 rejected（含平台 code 和可选 message），网络结果不明确则抛出可识别的 unknown-result 错误。
- request 使用 text／emoticon 互斥类型，不允许将独立表情 ID 当普通文字直接发出。

发送前检查有效会话及 bili_jct；按 PiliPlus 路径采用 WBI 签名和 multipart/form-data。使用 FormData 时由传输层生成 boundary，不手填不完整 Content-Type。秒级 rnd、roomid、csrf、csrf_token 及普通展示参数在请求层组装。

第一阶段先核对当前插件的 FormData 支持及实际序列化结果。若现有运行时不能正确传递 multipart，先报告实际问题再调整方案，不引入另一套 HTTP 服务。

### 状态与房间边界

只在主窗口保留一个发送状态控制器，按当前账号与真实房间保存运行期草稿，不持久化发送队列。关闭悬浮框、换页面或切换现场布局不清空草稿。

发送时固定本次账号、房间、内容和回复对象。切房、断线或退出登录时取消尚未发出的请求；已经提交的请求不承诺撤回。当前账号同一时刻只提交一个请求；发送过程中输入不可再次提交。切房收起输入框、隔离对应草稿和回复对象；迟到响应只能更新原请求的状态，不能清空新房间输入或弹出误导性的当前房间成功提示。

| 情况 | 用户看到的反馈 | 内容处理 |
| --- | --- | --- |
| 正在发送 | “正在发送…” | 防止重复发送，不自动关闭 |
| 接口明确返回正常发送 | “已发送” | 清理本次发送内容，保留回复对象及尚未发送的另一类草稿 |
| 内容被明确拦截 | “这条弹幕没发出去，请修改内容后再试。” | 保留内容 |
| 发送过快 | “发得太快了，稍等一下再发。” | 保留内容，不自动补发 |
| 字数超过平台允许范围 | “字数太多了，请缩短后再发。”；仅在知道准确上限时补充具体字数 | 保留内容，不自动拆分 |
| 账号被目标房间禁言 | “你在这个直播间被禁言了，暂时不能发送。” | 保留内容 |
| 登录失效或缺少发送凭据 | “登录已失效，请重新登录后再发。”；缺少凭据但登录仍有效时使用“请重新登录后再发。” | 保留内容，不暴露凭据名称 |
| 超时、中断，不能确定是否发出 | “没能确认是否发出，请先看看直播间，避免重复发送。” | 保留内容，不自动重试 |
| 明确失败但没有可解释的具体原因 | “没发出去，请稍后再试。” | 保留内容 |

反馈使用自然语言说明当前情况和下一步，不向用户展示“已提交”“平台接受”“回流”“广播”“CSRF”或错误码等内部表达。只有返回信息能支持具体原因时才显示对应提示，不把网络问题说成内容被拦截，也不把所有发送问题说成登录失效。“已发送”不附加“所有观众均已看到”等无法确认的承诺。成功反馈简短显示，不弹出额外确认框；失败反馈放在输入框附近，不打断修改和重试。

发送响应保留 code、message、msg 用于业务判断，不仅判断 HTTP 200。对有依据的拦截标记单独处理；未知非空信息不直接宣布已成功广播。第一版不承诺送达确认，不根据短时间内缺少回流认定发送失败。

事件列表只显示真实接收的弹幕，不插入模拟发送事件；现有统计、去重、归档、副窗口及 OBS 输出继续消费原接收链路。诊断仅记录阶段、结果、错误码和房间，不记录凭据、弹幕正文或完整响应体。

字数按 Unicode 字符计数；从可靠的账号／房间配置取得平台上限后再据此限制。无法确认上限时只展示当前字数、保留平台长度错误提示，不把参考项目的默认 20 字或 5 秒间隔当作平台规则。明确限流时提示等待，不自动排队补发。

## 待确认的交互默认值

1. 独立大表情采用“选择预览，再点击发送”，不采用点选即发。
2. 首版回复只在当前现场启用；回看及只读输出不提供回复发送入口。
3. 常用语在本轮基础链路之后另行规划，不与首版三个核心能力同时扩张。

上述默认值作为首版实现边界。表情与回复能否组合属于平台验证事项，不以界面设计替代实测。

## 表情与粉丝牌完善

1. 表情请求附带平台设备信息，完整读取直播小表情和当前账号的个人包；按类型与包编号区分分类。单项 perm 决定可用性，不用小表情包的 pkg_perm=0 禁用全部表情。
2. 输入框取消可见标题，每次打开收起表情。图片分类保留无障碍名称，小表情混排、粘贴与复制沿用平台触发词，字数按发送文本占用计算；大表情点击即发并保留文字、回复草稿。
3. 顶部标题行常驻原生粉丝牌，不重复用户名，读取佩戴及点亮状态，展开列表切换；加载更多及刷新由粉丝牌区域负责，切换成功后更新表情权限。
4. 验收覆盖输入法、光标插入、删除、收起重开、锁定表情、个人包、粉丝牌切换失败、切房、四语言及100%／125%／150%缩放。真实发送与佩戴变更需用户在正式程序中操作。

粉丝牌切换列表合并平台单独返回的当前佩戴项；收起和展开均复用 FanMedalBadge。表情分类条支持滚轮横移与键盘切换。小表情格32px、图片24px，大表情格48px，通用长条行高28px，各类图片保持比例。

## 发送响应优化

- 打开发送框时复用粉丝牌的房间信息读取准备网络连接，不增加重复查询；表情面板展开后在权限到期前一分钟刷新，收起后停止定时刷新，保留当前分类。
- 发送结果日志记录各阶段毫秒数：组装、账号准备、表情权限、签名、内容编码、内部提交、平台回应及读取、结果处理和总耗时。平台回应耗时包含网络及平台处理，内部提交包含平台回应，两者不相加；日志不保存弹幕内容和请求凭证。

- 房间连接完成后在后台准备发送网络连接，不进入进房或事件接收的等待链；准备失败不改变连接状态。切房取消旧房间等待，新房间独立准备。
- 发送与房间用户信息查询使用持久 HTTP 客户端，完整读完响应后复用底层连接；不依赖 OBS 开启。并发房间信息读取合并，完成后不缓存佩戴状态。
- 发送保留可取消句柄和十五秒等待上限，不自动重试。通过本机接口验证连接复用及取消，不向直播间发送测试消息。

- 入口使用带加号的对话气泡，明确表示新建弹幕。
- 连接就绪后并行准备账号验证、WBI 签名材料和设备信息；输入框打开时预备即将到期的数据，近期结果保留五分钟。
- 表情面板与发送请求共用请求层的表情数据及权限；合并同时发生的准备请求，手动刷新、账号变化及切换粉丝牌使对应结果失效。
