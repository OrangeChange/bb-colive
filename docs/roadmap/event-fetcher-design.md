### 产品命名

软件产品统一使用 **BB**，采集服务名称为 **BB EventFetcher**，服务项目目录及独立私有仓库名为 `bb-event-fetcher`。本文中的 EventFetcher 为采集服务简称。

现有客户端源码目录 `danmu-app`、代码类型 `DanmakuEvent` 及已有技术标识按实际名称引用；产品名称与源码路径分别管理。

## 一、目标

EventFetcher 是由 BB 用户自行部署的私人 B 站直播数据采集服务。它在用户电脑未运行 BB 时继续监听用户明确配置的直播间，并在客户端恢复后提供缺失数据。

第一版必须做到：

- 所有 B 站连接必须使用有效登录态；
- 保存服务端实际收到的完整原始命令，而不是只保存付费事件；
- 记录连接、登录、写入和服务重启造成的数据缺口；
- 不把存在已知缺口的直播场次标记为完整；
- BB 能按场次和游标断点拉取缺失数据；
- 云端原始数据由客户端当前版本的协议与业务适配器转换为本地标准事件；
- 默认保存最近 30 天，允许用户配置其他期限或永久保留；
- 保存每场直播实际使用过的直播封面文件；
- 保持个人部署简单，不建设公共数据平台。

“完整”表示从已确认的开播到已确认的下播之间没有检测到登录、连接、进程或数据库写入缺口。它不表示能够证明 B 站服务端下发了所有理论上存在的事件。

## 二、明确边界

### 2.1 私有部署

- 每个 EventFetcher 实例属于一个用户。
- 用户自行选择服务器、域名、存储和保留期限。
- 只采集用户在 BB 中明确启用的直播间。
- 项目不运行公共采集集群，不提供主播公共数据库。
- 不允许不同用户查询、共享或交换直播数据。
- 项目维护者不接触用户的 B 站凭证和实际直播数据。

### 2.2 仅采集数据

EventFetcher 只保存采集所需配置和直播数据，不同步 BB 的个人状态。

服务端不保存：

- 收藏；
- 用户昵称；
- 阅读位置；
- 界面设置；
- TTS 或个性播报设置；
- 窗口布局；
- 本地问题标记。

这些状态始终由 BB 本地管理。

### 2.3 第一版不做

- 公共采集服务器；
- 多用户注册、组织、角色和权限系统；
- 公共查询、分享链接和数据交易；
- 云端生成并永久保存完整 `DanmakuEvent`；
- 服务端礼物连击合并；
- 云同步收藏、昵称、阅读位置或软件设置；
- 保存主播头像或观众头像文件；
- 下载礼物图标、弹幕表情和礼物特效文件；
- 网页版完整管理后台；
- Redis、消息队列、微服务、多节点集群或自动分片；
- 复杂密钥轮换和迁移框架；
- 数据分析、排行榜和统计看板。

## 三、总体架构

```text
                         ┌──────────────────────────────┐
                         │ 共享 B 站直播协议包          │
                         │                              │
                         │ 拆包 / 解压 / 心跳 / 解码    │
                         │ 命令识别 / 稳定标识提取      │
                         └──────────┬───────────────────┘
                                    │
                   ┌────────────────┴────────────────┐
                   │                                 │
        ┌──────────▼──────────┐           ┌──────────▼──────────┐
        │ BB                  │           │ EventFetcher         │
        │                     │           │                      │
        │ 本地实时连接        │           │ 多房间常驻采集       │
        │ 业务 adapter        │           │ 原始事件持久化       │
        │ DanmakuEvent        │           │ 场次与缺口记录       │
        │ SQLite 回看档案     │◄─HTTPS───►│ 同步 API             │
        │ 展示/TTS/礼物合并   │           │ 扫码登录页           │
        └─────────────────────┘           └──────────┬───────────┘
                                                     │
                                          ┌──────────▼───────────┐
                                          │ PostgreSQL + 数据卷  │
                                          └──────────────────────┘
```

EventFetcher 是独立服务，但不另写一套 B 站底层协议实现。桌面端与服务端共享连接和解码代码，产品语义继续留在 BB。

## 四、技术路线与部署

### 4.1 技术选型

- TypeScript；
- Node.js LTS；
- PostgreSQL；
- Docker Compose 作为正式支持的服务器部署方式；
- 单个 EventFetcher 服务进程；
- 不强制 Redis；
- HTTPS 由 Caddy、Nginx 或用户已有反向代理提供。

选择 TypeScript 是为了共享当前协议代码，避免桌面端和服务端的拆包、心跳、protobuf 解码及命令识别逐渐分叉。第一版不采用 Rust 重写，也不拆分独立采集进程。

### 4.2 部署形态

正式部署包含：

```text
event-fetcher     Node.js 服务
postgres          PostgreSQL 数据库
event-data        封面文件与服务数据卷
reverse-proxy     用户已有或自行选择，不强制捆绑
```

服务器最低规格在实现和压力测试后根据真实数据确定，不在设计阶段编造固定数值。第一版面向个人少量房间，默认配置上限为 10 个直播间；达到上限后明确提示，不自动移除旧房间。

### 4.3 内部模块

- `auth`：B 站扫码登录、凭证导入、保存及有效性检查；
- `rooms`：真实房间号解析与采集清单；
- `collector`：连接准备、KeepLiveWS、重连和房间隔离；
- `protocol`：引用共享协议包；
- `sessions`：直播场次和生命周期；
- `storage`：原始事件、索引、连接区间和故障记录；
- `sync-api`：供 BB 查询和分页同步；
- `retention`：按场次执行保留期清理；
- `health`：服务、账号、房间、连接和数据库状态；
- `web`：极简扫码登录页。

这些是单体服务中的代码模块，不是微服务。

### 4.4 仓库与共享代码维护

- BB EventFetcher 使用独立的私有 Git 仓库，与客户端仓库并列存放。
- 客户端可独立开源，构建不依赖 EventFetcher 私有仓库。
- 共享协议包在客户端仓库的 `packages/bilibili-live-protocol` 中维护，独立声明版本；服务端通过固定版本的包产物引用，构建不依赖本机相邻目录。
- 两端锁定共享协议包及 `@laplace.live/ws` 的具体版本，协议升级同时验证两端连接与解码行为。
- Git 保存源码、设计和部署模板；凭证、实际配置中的密钥、数据库与采集文件保存在部署环境。

## 五、共享代码与职责划分

### 5.1 共享协议包

从客户端源码提取一个无 UI、无 Tauri 依赖的 TypeScript 包。现有 `@laplace.live/ws` 继续作为共同依赖，使用同一锁定版本；不复制它的源码另行维护。以下传输能力由该依赖提供，项目共享包负责接入、公共连接准备和自身的命令解码：

- B 站 WebSocket 数据包编码与拆包；
- Brotli、zlib 解压；
- join 鉴权包；
- 心跳、超时和自动重连；
- JSON 与 protobuf 解码；
- 命令识别；
- 原始事件信封类型；
- 每种命令可直接证明的业务标识提取；
- WBI 签名等纯逻辑；
- 真实协议样本测试。

共享包不负责：

- UI 状态；
- Tauri HTTP 传输；
- 完整 `DanmakuEvent` 业务转换；
- 礼物金额产品口径；
- 盲盒、互动和展示分类；
- 礼物连击合并；
- TTS、特效或回看投影。

HTTP 请求规则、WBI 签名和命令解码可以共享；桌面端的 Tauri HTTP 与服务端的 Node.js HTTP 分别提供传输实现。当前 `DanmuConnection` 包含客户端诊断和业务适配调用，提取共享能力时保留纯协议边界。

### 5.2 桌面端职责

- 当前房间的本地实时采集；
- 原始事件到 `DanmakuEvent` 的业务适配；
- 本地与云端事件去重；
- 礼物连击渲染合并；
- SQLite 回看档案；
- 收藏、昵称、阅读位置；
- 展示、筛选、TTS、个性播报和礼物特效。

### 5.3 EventFetcher 职责

- 7×24 小时管理多个房间连接；
- 保存实际收到的原始命令；
- 保存必要的稳定索引和采集证据；
- 记录场次、连接区间和已知缺口；
- 保存直播封面；
- 提供带鉴权的同步 API；
- 执行保留期清理。

## 六、B 站登录

### 6.1 强制登录态

- EventFetcher 不提供匿名采集模式。
- 建立直播连接前必须存在经过验证的 B 站登录态。
- 确认登录失效时关闭相关采集连接并暂停采集，重新验证成功后恢复。
- 失效被发现前已收到的数据仍保留；从最后一次成功验证到确认失效之间标记为登录有效性未确认区间，不声称知道准确失效时刻。
- 登录验证请求超时或网络失败属于“验证暂不可用”，不能直接判定 Cookie 失效。现有连接的最后验证时间和验证异常必须可见；尚未完成首次验证时不得启动连接。

有效登录态能够提高事件和字段覆盖率，但不能证明 B 站一定下发了所有理论事件。

### 6.2 独立扫码登录

EventFetcher 提供极简登录页：

```text
https://<event-fetcher-host>/login/<one-time-session>
```

时序如下：

1. BB 使用服务器访问令牌请求创建一次性扫码会话。
2. EventFetcher 调用 B 站二维码登录接口。
3. EventFetcher 返回短期登录页地址。
4. BB 使用系统浏览器打开该地址。
5. 页面显示二维码和等待扫码、等待确认、成功、过期或失败状态。
6. 用户使用哔哩哔哩手机客户端扫码并确认。
7. EventFetcher 在服务器内部轮询结果。
8. 成功后，B 站凭证直接加密写入服务器存储。
9. 页面只显示成功状态和账号摘要，不显示 Cookie。
10. BB 通过正式鉴权接口读取新的登录状态。

一次性登录会话只能完成本次扫码，不能查询历史、修改房间或替换其他设置，到期后立即失效。

### 6.3 从 BB 导入登录态

作为高级路径，BB 可以把当前 B 站登录态提交给用户自己的 EventFetcher：

- 必须由用户主动操作并单独确认；
- 明确显示目标服务器地址和将发送的凭证类型；
- 只允许通过 HTTPS；
- 服务端验证账号后立即加密保存；
- 响应只包含账号摘要和验证结果；
- 不进行自动、静默或周期性 Cookie 上传。

### 6.4 登录态失效

- 记录失效时间和错误类别；
- 停止无意义的完整连接准备重试；
- 当前直播场次立即增加登录缺口；
- BB 设置页提示重新扫码；
- 重新登录后恢复采集；
- 失效期间的缺口不会因为恢复登录而被清除。

## 七、服务器连接与房间生命周期

### 7.1 复用当前稳定连接

EventFetcher 第一版使用与 BB 相同的 `@laplace.live/ws` `KeepLiveWS` 连接核心：

- 使用登录 UID、弹幕 token 和 buvid；
- 默认协议版本 3；
- 进入房间后立即发送心跳；
- 收到心跳响应后约 30 秒发送下一次心跳；
- 45 秒没有心跳响应则关闭连接；
- 断开后等待 3 秒创建新 WebSocket；
- 使用相同的拆包、解压和消息分发实现。

上述行为对应当前客户端实际安装的 `@laplace.live/ws 8.0.4`。两端复用该连接核心，升级依赖时按第十九节验证连接、解压与消息分发行为。

### 7.2 长期运行监督器

KeepLiveWS 负责短暂网络故障。EventFetcher 在其外层增加常驻服务需要的监督能力：

- 每个房间独立运行，单个房间失败不影响其他房间；
- 记录每次连接开始、成功、断开和恢复；
- 重连成功后重新查询房间直播状态和标准化开播时间，查询失败时保留直播状态未知；
- 房间查询结果只应用于对应连接代次，且不得覆盖请求发出后收到的新开播或下播证据；
- 持续失败时重新执行完整连接准备流程，重新取得 host 和 token；
- 登录失效时停止普通重连并进入待登录状态；
- 进程重启后恢复启用房间和未结束场次；
- 已确认发生在同场直播期间的停机区间记录为采集中断；范围或场次归属尚未确认时保留疑似缺口及依据。

实现阶段应根据真实失败类型决定何时从 KeepLiveWS 短时重连升级为完整重连，不在设计中增加与故障无关的复杂退避框架。

### 7.3 房间管理

- 用户在 BB 中为主播开启“云端采集”。
- BB 把真实房间号加入 EventFetcher 清单。
- EventFetcher 随即开始监控，不要求 BB 保持运行。
- 登录有效时，启用的房间持续保持 WebSocket 连接，包括未开播期间；HTTP 低频状态检查用于核对状态和恢复场次。
- 原始事件先按房间保存，再关联直播场次；未开播期间的事件允许没有场次归属，仍可同步。
- 临时断线和重连后按第十节证据判断是否续接原场次。
- 下播后结束场次，保持连接以收集未开播期间事件并捕获下一次开播。
- 用户从清单移除主播后停止未来采集。

移除时提供：

1. 仅停止采集，历史继续按保留策略保存；
2. 停止采集并删除该主播云端历史。

第二种操作必须显示场次数量、事件数量、封面文件数量和影响范围，并在执行前再次确认。

## 八、原始事件存储

### 8.1 单一权威数据

EventFetcher 持久化数据中的权威事实是原始采集事件，不保存第二份完整标准事件 JSON。持久化受保留期限约束，不意味着永久保留。

在 `KeepLiveWS` 的原始 `msg` 入口记录接收时间、分配房间序号并排队保存，先于业务适配和头像等资料的异步补取。接收顺序以原始命令到达该入口的顺序为准，不使用客户端最终 `onEvent` 回调的顺序；资料请求的延迟或失败不阻塞原始采集。

每条事件使用采集信封：

```text
room_id
session_id (可空)
server_sequence
received_at
bilibili_timestamp
command
protocol_version
raw_payload
connection_id
login_account_uid
quality_flags
```

原始载荷只保存一次。数据库另提取少量用于分页、查询和确定性去重的字段，例如：

- B 站事件 ID；
- 用户 UID；
- 基础命令类别；
- 是否为付费事件；
- 礼物、SC、大航海等命令自身提供的业务 ID；
- `combo_id` 等原始字段；
- 事件发生时间。

这些索引不是 BB 的完整业务语义。

### 8.2 JSON 与 protobuf

- JSON 命令保存解压后、业务适配前的完整对象，包括 protobuf 命令的外层字段和原有 `data.pb` 等编码载荷。
- 外层对象已经包含可还原的 base64 protobuf 时，不再重复保存相同二进制和完整解码 JSON；查询所需字段由索引提取器生成，并记录其版本。
- 如果接收接口直接提供独立二进制，则保存该二进制及必要外层字段。
- 命令解码失败仍保存原始载荷和失败状态，不阻断后续命令写入。
- 这里的原始数据指命令级内容，不要求额外保存压缩网络帧、心跳包或 TCP 流。

### 8.3 未识别命令

- 未识别命令同样写入原始事件表。
- 它们默认不进入 BB 的普通回看事件列表。
- 新版客户端支持该命令后，可以用保存的原始数据重新生成本地标准事件。

### 8.4 礼物连击

服务器不处理连击：

- 收到一条保存一条；
- 不累计数量；
- 不覆盖先前事件；
- 不重算金额；
- 不把 `SEND_GIFT` 和 `COMBO_SEND` 合成一条；
- `combo_id` 只作为原始字段或查询索引保留。

连击展示合并继续由 BB 当前业务逻辑完成。

### 8.5 历史解析与保留期限

- 默认支持云端保留的最近 30 天原始数据重新拉取和解析；用户调整保留期限后，以实际可用范围为准。
- 本地档案保存标准事件、来源记录标识、解析版本和必要关联，不要求永久保存同步原文。
- 云端原始数据过期后，本地标准事件按本地档案规则继续保存；不保证可以重新解析或修复当时的解释。
- 未识别命令以后能否补解析，同样取决于原始记录是否仍在保留期内。

### 8.6 采集上下文快照

部分资源不在 WebSocket 报文中。现有 `gifts.ts` 从礼物配置取得盲盒本体图标，`giftEffects.ts` 从独立配置取得视频地址及播放参数，因此采集时还须保存这些 HTTP 配置结果。

- 建立采集和创建场次时获取房间资料、礼物目录和特效配置；房间资料包含主播 UID、标题、封面、平台开播时间以及大航海人数和档位等原始字段，供客户端还原 `RoomGuardProfile`；协议通知或资源引用未命中时按需刷新。
- 配置缓存与快照按房间隔离；事件引用接收时该房间可用的快照，不使用其他房间或当前页面的配置代替。
- 每份快照记录房间、来源接口类别、获取时间、结果及原始配置内容；失败不阻塞 WebSocket 接收。
- 事件解析使用接收时已取得的对应快照。首次获取或后续补获的数据标注获取时间，不声称它就是未知的历史配置。
- 多条事件引用同一份快照，不逐事件复制目录，不下载封面以外的媒体文件。
- 客户端同步事件时取得对应快照；配置缺失时保留文字与原始标识，并显示资源信息不完整。
- 快照随引用它的保留期内数据保管，最后一个引用到期后可清理。

## 九、图片与媒体资源

### 9.1 直播封面

第一版唯一下载并保存为文件的媒体资源是直播封面。

每场直播保存：

- 原始封面 URL；
- 文件资源 ID；
- 文件相对路径；
- MIME 类型；
- 字节数；
- 获取时间；
- 首次发现时间和下一版本发现时间；
- 上游明确提供的变更时间（可空）及时间来源；
- 获取成功或失败状态。

在以下时机获取封面：

- 场次创建时；
- 收到封面或房间信息变化事件时；
- 状态检查发现封面 URL 变化时。

一场直播可以保存多个封面版本。封面文件放在 EventFetcher 数据卷，不存入 PostgreSQL；数据库只保存元数据和相对路径。

轮询只能证明何时发现变化，不能证明准确生效时间。封面审核通知只触发重新查询房间实际封面，不直接认定审核成功或已经换图。下载成功后才发布文件引用，失败保留 URL 和错误状态。

### 9.2 其他资源

下列资源只保存原始 URL、标识、宽高和事件中已有的元数据，不保存文件：

- 主播头像；
- 观众头像；
- 礼物静态图、WebP 和 GIF；
- 盲盒图标；
- 弹幕大小表情；
- 礼物特效视频、WebM、SVGA 等资源。

礼物特效的 ID、类型、URL、触发参数和原始命令必须保留。

“缓存事件媒体资源”可以在后续作为高级选项评估，但不进入第一版。在得到真实容量和资源失效率前，不预先实现媒体归档系统。

## 十、直播场次与完整性

### 10.1 场次创建和结束

- 检测到开播后创建服务端场次 ID。
- 场次 ID 不依赖标题或客户端时间。
- 平台开播时间、实际开始采集时间和是否捕获开播边界分别记录；中途开始采集不等于平台开播时间未知。
- 平台开播时间统一标准化为毫秒时间戳；临时断线和服务重启后，以真实房间号及相同的平台开播时间确认同场，不续接已确认结束的场次。
- `live_key`、`sub_session_key` 保留在原始命令中，不作为同场合并依据。
- 收到可归属当前场次的可靠下播事件，或平台查询明确确认该场已结束后，标记已结束。
- 未取得可靠结束证据时保留直播状态未知；已确认结束但无法取得准确结束时刻时，结束时间仍为空，并记录发现已结束的时间。
- 发现新的明确开播周期时，旧异常场次按证据结束或分离，不能因为标题变化拆场。

“当前仍在直播”不足以证明与停机前同场；停机期间可能下播后再次开播。能证明同场时续接，能证明新场时创建新场，证据不足时先保存为归属待确认事件。已知开播时间与是否完整捕获开场分别记录，不能混为一项。

本地与云端场次建立独立映射，按真实房间号及标准化平台开播时间匹配；仅时间重叠或标题相同不够。不能可靠匹配时保留待确认记录，不强行合并。后续归属修正通过元数据更新传给客户端，不修改原始事件身份或重新分配其序号。

### 10.2 连接区间

每次成功连接形成一个连接区间，记录：

- 连接 ID；
- 房间号，以及该连接覆盖的场次关联；
- 开始和结束时间；
- 使用的登录账号 UID；
- 登录态是否有效；
- 断开原因；
- 是否恢复；
- 是否形成已知缺口。

### 10.3 状态与质量

直播状态、记录状态、记录质量和数据可用性分别保存：

- 直播状态：`ongoing`（进行中）、`ended`（已结束）、`unknown`（状态未知）；断连或停止采集不能作为下播证据。
- 记录状态：`recording`（记录中）、`reconnecting`（重连中）、`stopped`（已停止）；描述服务端对该场的采集状态。
- 记录质量：`pending`（待确认）、`complete`（完整）、`incomplete`（不完整）。已确认中途开始采集、直播期间采集中断或数据丢弃时为不完整；边界可靠、无已知缺口且待写数据全部处理完成后才可判完整；其他情况为待确认。
- 已确认的质量原因按集合保存；停止原因、边界未知、登录有效性未确认、疑似缺口和场次归属待确认分别记录，不混为已确认丢失。
- 可用性：`available`、`expired`、`deleted`，与上述状态独立。

例如一场可以同时是进行中、记录中、不完整；缺少平台开播时间本身只表示证据不足，不证明漏采。恢复记录不清除此前已确认的缺口。场次结束后该场记录停止，房间连接仍可继续采集未开播期间的原始命令。

质量判断考虑：

- 是否捕获开播；
- 是否捕获下播；
- 登录态是否全程有效；
- WebSocket 连接区间；
- 服务进程停机区间；
- 房间是否直播中途才加入；
- 数据库是否存在未恢复的写入失败；
- 是否发生待写队列溢出和事件丢弃。

短暂数据库失败但全部排队记录最终成功提交，不单独形成不完整结论。存在未解决的写入、登录或边界疑点时不能判完整；已有确定缺口则继续保持不完整。

结束状态与数据质量是两个概念。已经下播不等于采集完整。

## 十一、顺序、去重与合并

### 11.1 服务端顺序

EventFetcher 为每个房间分配单调递增的 `server_sequence`，表示服务端接收顺序。它不替代 B 站事件时间。

可靠同步以房间序号为主，场次作为查询和展示维度；这样未归属事件及其后续关联不会漏同步。稳定来源身份为 `server_id + room_id + server_sequence`，`server_id` 在同一数据库生命周期内保持不变，重建空数据库时使用新 ID。

每个房间串行提交批次，原始事件和已提交进度在同一事务中写入。API 只发布已持久化、且之前记录均已写入或明确登记丢失的进度；不能先暴露大序号，再补写客户端已越过的小序号。序号不要求连续，单凭数值跳号不能断言丢事件。

### 11.2 原始记录边界

原始事件在业务去重之前保存，与当前 BB 的 source 诊断流一致：

- 能确认是服务器重推的记录可以标记为重复；
- 重复标记不能删除原始证据；
- 无法证明重复时保留记录；
- 不为所有事件增加通用哈希或内容指纹。

去重应优先使用各命令自身提供的事件 ID、消息 ID、业务 ID或项目已有的可解释复合键。

### 11.3 客户端去重

云端事件进入 BB 后：

1. 使用当前版本共享协议包读取；
2. 使用客户端 adapter 转为 `DanmakuEvent`；
3. 先按稳定来源记录 ID 保证重复导入幂等，再按各事件专用业务键匹配本地与云端记录；
4. 与本地实时采集事件合并为同一场档案；
5. 记录事件来源为本地、云端或两者均收到；
6. 礼物连击在读取或渲染时合并。

当前 adapter 中的 `Date.now()` 和运行期计数 ID 不能直接用于历史重放。解析上下文必须包含原始接收时间、稳定来源 ID、当时房间资料与配置快照。缺少上游时间时使用采集时的接收时间；缺少上游 ID 时用来源 ID 和确定的输出子序号标识解析结果。重复解析同一记录得到相同身份和时间。

不同来源记录的来源 ID 不同，不能据此跨端去重。仅在各命令的业务标识足以证明同一事件时合并，并保留两份来源关联；无法可靠匹配时保留并标注，不能按用户名、金额和临近时间直接吞并。长期导入幂等依赖本地持久化唯一约束，不依赖现场的 20,000 条内存 Map。

保留期内重新解析时，按来源记录关联更新派生内容，保留本地收藏等关联；已无法匹配的关联必须提示。历史同步只更新本地档案，不自动触发 TTS、个性播报、礼物特效或副窗口实时投递，不创建副窗口固定卡片，也不启动或重置其停留计时。

## 十二、同步协议

### 12.1 基本原则

- 服务器提供原始数据，客户端决定当前业务语义；
- 按房间同步原始记录，以场次组织档案；
- 按服务端序号分页；
- 标准事件、来源关联和本地同步游标在同一 SQLite 事务中提交；
- 重复请求同一页必须安全，不产生重复档案事件；
- 服务器保留策略不依赖某台客户端的已读进度；
- WebSocket 只做状态和新数据通知，不承担唯一可靠传输。

### 12.2 自动同步时机

BB 在以下时机检查云端：

- 应用启动并恢复本地会话后；
- 连接已启用云端采集的主播时；
- 网络恢复后；
- 打开该主播回看页时；
- 用户点击“立即同步”时；
- 应用运行期间的低频周期检查。

### 12.3 同步流程

```text
查询云端房间场次及元数据修订
  → 对比本地场次映射和房间同步游标
  → 获取已提交进度、可用范围及清理记录
  → 分页拉取缺失原始事件
  → 当前 adapter 生成 DanmakuEvent
  → 与本地事件去重和合并
  → 同一 SQLite 事务提交事件、来源和游标
```

分页返回 `items`、`next_cursor`、`committed_through` 和 `has_more`。客户端推进服务端返回的扫描游标，不用当前页面最后一条“成功解析事件”的 ID 推断进度；未知命令也必须推进采集记录游标。

场次结束状态、缺口、封面、配置快照和归属修正使用独立的房间元数据修订号。即使没有新事件，客户端仍获取修订并在本地事务应用后更新元数据游标。场次归属修正包含受影响的来源记录标识或序号区间。

首次同步从实际保留范围开始。已有游标跨过清理范围时，服务端返回已清理区间和原因，客户端标记不可补回范围；不能仅凭最小序号推断丢失。分页期间遇到数据到期也按此规则处理，不锁住服务器保留策略。

### 12.4 客户端集成边界

以下行为属于 BB 的本地同步、档案和回看职责，不要求 EventFetcher 在服务端实现界面或业务投影：

- 无场次归属的记录和场次归属待确认的记录，由客户端决定在回看中放入“非直播期间”或“待确认”范围；服务端只需通过房间增量接口提供这些记录，并在归属修订后发布更新。
- 本地实时连接与云端记录被客户端判断为同一业务事件时，由客户端按来源记录 ID 和事件专用业务键合并。服务端保留原始记录和来源，不决定本地标准事件字段的优先级。
- 封面文件由服务端保存并通过鉴权接口提供，客户端同步档案时是否下载到本地资源目录、何时重试及本地档案删除时如何处理，属于 BB 的资源策略。云端封面过期后，服务端只保证在保留期内可用，不要求客户端继续依赖远端地址。
- 荣耀等级、用户大航海图标等连续消息上下文由客户端在历史解析时按房间和顺序重建，跨分页保持一致；缺少可恢复的历史依据时保留未知，不使用当前实时连接的缓存补造历史。
- 头像可能来自原始命令、同连接已观测资料或额外 HTTP 请求；原始命令不包含客户端后来通过 HTTP 补取的结果。头像补全属于客户端职责，后补资料不作为采集当时的资料，无法还原时保留缺失或使用客户端默认头像。头像缺失不影响采集完整性，服务端仍只保留原始数据中已有的头像 URL，不下载头像文件。
- 自动弹幕、手机号验证状态和金额的解释与显示筛选属于客户端。服务端保留原始字段及编码载荷，不因客户端隐藏事件而跳过采集，也不根据显示结果重算支付金额。
- 当前客户端已有 SQLite 档案和本地档案包导入导出；云端来源记录映射、同步游标、解析版本及跨源关联由客户端接入阶段补齐。
- 服务端记录状态表示云端采集状态，不能直接覆盖客户端本机的记录状态；两端场次状态与质量的映射、合并由客户端处理。

这些客户端职责不会改变 EventFetcher 的原始采集、顺序提交、保留和同步 API 契约，也不作为服务器采集完整性的判定条件。

## 十三、API 边界

所有 `/api/v1` 管理和读取接口均要求服务器访问令牌，扫码登录的一次性页面除外。

### 13.1 服务与登录

- `GET /api/v1/info`：稳定服务器 ID、服务版本、API 版本、共享协议版本、数据库和保留策略；
- `PATCH /api/v1/settings`：设置保留期限或永久保留；缩短期限前展示预计清理影响并由用户确认；
- `GET /api/v1/auth/status`：B 站登录状态和账号摘要；
- `POST /api/v1/auth/qr-session`：创建一次性扫码会话；
- `POST /api/v1/auth/import`：高级方式导入登录态；
- `DELETE /api/v1/auth`：退出账号并清除 B 站凭证。

### 13.2 房间

- `GET /api/v1/rooms`：采集清单和状态；
- `POST /api/v1/rooms`：添加真实房间号；
- `DELETE /api/v1/rooms/<room_id>`：仅停止，或停止并删除历史；
- `GET /api/v1/rooms/<room_id>/status`：房间连接和采集状态。

### 13.3 场次与事件

- `GET /api/v1/rooms/<room_id>/events?after=<sequence>&limit=<n>`：可靠增量同步入口，包含无场次归属记录；
- `GET /api/v1/rooms/<room_id>/sync-state`：已提交进度、可用范围和已清理区间；
- `GET /api/v1/rooms/<room_id>/changes?after=<revision>`：分页读取元数据修订及必要快照；

- `GET /api/v1/rooms/<room_id>/sessions`：分页查询保留期内场次；
- `GET /api/v1/sessions/<session_id>`：场次元数据、质量和连接区间；
- `GET /api/v1/sessions/<session_id>/events?after=<sequence>&limit=<n>`：分页读取原始事件；
- `GET /api/v1/sessions/<session_id>/events/range`：该场次可用序号、数量和保留状态，不作为房间增量同步游标；
- `GET /api/v1/sessions/<session_id>/covers`：封面版本和文件访问地址；
- `GET /api/v1/stream`：可选状态通知通道。

第一版不提供任意 SQL 风格筛选、公开搜索或跨用户接口。

## 十四、核心数据实体

### 14.1 `bilibili_account`

- UID、昵称和头像 URL；
- 加密登录凭证；
- 登录时间和最近验证时间；
- 当前有效状态和失效原因。

### 14.2 `monitored_room`

- 真实房间号、主播 UID；
- 主播名称和头像 URL；
- 是否启用采集；
- 添加、停止时间；
- 当前连接状态；
- 最近成功事件时间。

### 14.3 `live_session`

- 服务端场次 ID；
- 房间号和主播信息快照；
- 直播标题、分区；
- 平台开播时间 `source_live_started_at`（毫秒，可空）、实际开始采集时间 `capture_started_at`、是否捕获开播边界；
- 可靠结束时间（可空）、结束证据来源、发现已结束时间；
- 直播状态、服务端记录状态、最近停止采集时间和停止原因；
- 数据质量状态、已确认质量原因集合及尚未确认的证据；
- 最小、最大事件序号；
- 事件数量；
- 到期时间。

### 14.4 `connection_interval`

- 房间和连接 ID、覆盖的场次关联；
- 开始、结束时间；
- 登录状态；
- 断开与恢复原因；
- 缺口起止和质量影响。

### 14.5 `raw_event`

- 房间号、可空场次 ID 和房间内唯一服务端序号；
- 接收时间和 B 站事件时间；
- 命令名、协议版本；
- B 站事件 ID、用户 UID和必要索引；
- 原始 JSON 或二进制；
- 索引提取版本、配置快照关联及解码失败状态；
- 连接 ID；
- 已确认的重复关系和质量标记。

### 14.6 `session_cover`

- 场次 ID和资源 ID；
- 来源 URL和文件相对路径；
- MIME 类型和字节数；
- 获取时间和结果；
- 发现区间、可空上游变更时间及时间来源。

### 14.7 `collector_issue`

记录可能影响数据完整性的故障及其恢复结果：

- 登录失效；
- WebSocket 断开；
- 完整重连失败；
- 服务重启；
- 数据库写入失败；
- 待写队列溢出；
- 直播途中才加入房间。

故障记录包含发生、恢复或尚未恢复的状态，以及已确认缺口或待确认的质量影响。可重试写入故障的存在本身不表示数据已丢失；批次全部成功提交后保留故障事实及恢复结果。

该表不复制每条事件日志。

### 14.8 配置与同步进度

- `room_snapshot`：按房间保存房间资料（含大航海人数与档位）、礼物目录和特效配置的原始快照、来源、获取时间及结果；
- `room_sync_state`：房间已提交序号、元数据修订号、最后持久化采集进度和连接存活检查时间；
- `room_change`：场次、封面、缺口及事件归属更新的修订记录；
- `retention_range`：按房间保存已删除的序号区间和原因；相邻同原因区间合并，不保存已删除的事件正文、用户信息或封面。

场次删除后保留最小删除标记，以便已经同步该场次的客户端识别过期或主动删除。停止采集不删除房间同步身份和序号进度。

## 十五、保留与删除

### 15.1 默认策略

- 默认保留最近 30 天；
- 用户可配置其他期限或永久保留；
- 已结束场次按结束时间加保留期限整场清理；因此场次早期事件可能略超过 30 天，设置说明须明确这一口径；
- 记录中或重连中的场次暂不清理；已停止记录且缺少直播结束证据的场次，以停止采集时间作为清理基准。确认已下播但不知道准确结束时刻时，以发现已下播的时间作为清理基准，仍保留结束时间未知标记；
- 无场次归属记录按接收时间加保留期限清理，不因归属不明永久保留；
- 正在写入或重试的批次完成后再清理其数据，不因客户端尚未同步而延长保留；
- 原始事件、对应故障与关联、封面文件到期清理，共享快照和连接区间在最后一个保留期内引用消失后清理；最小删除标记保留。

### 15.2 主动删除

支持删除指定主播的云端历史。执行前必须计算并显示：

- 场次数量；
- 原始事件数量；
- 封面文件数量；
- 占用空间；
- 将失去的可同步日期范围。

未经确认不得删除。删除成功后需要说明删除内容及不可从 EventFetcher 恢复；已经同步到 BB 本地的档案不受影响。

## 十六、安全边界

### 16.1 服务访问令牌

- 部署时设置或首次启动生成；
- BB 使用 `Authorization: Bearer`；
- 不在 URL 中传递；
- WebSocket 使用请求头或建立连接后的首条鉴权消息；
- 客户端使用系统安全凭证存储，不写入普通设置 JSON。

### 16.2 B 站凭证

- 使用部署环境提供的 `CREDENTIAL_SECRET` 加密后写入 PostgreSQL；
- 密钥不写入数据库；
- 接口、日志和错误信息不得返回 Cookie；
- 缺少或无法使用密钥时不加载凭证，并要求用户修复配置或重新登录；
- 第一版不建设密钥轮换框架，只支持清除凭证并重新登录。

### 16.3 网络

- 公网服务器必须使用 HTTPS；
- `localhost` 可以使用 HTTP；
- 局域网 HTTP 只能作为用户明确启用的开发模式，不作为默认部署建议。

### 16.4 日志脱敏

可以记录房间号、命令名、连接状态、数据库结果、事件数量和必要账号摘要。不得记录：

- Cookie；
- 服务访问令牌；
- 扫码登录密钥；
- Authorization 请求头；
- 包含凭证的数据库连接字符串。

第一版只有一个服务所有者，不引入注册、角色和多租户模型。

## 十七、BB 设置入口

新增“设置 → 云端采集”，提供：

- 启用云端采集；
- EventFetcher 服务器地址；
- 连接、检测和解除绑定；
- 服务版本、API 兼容状态和数据库健康状态；
- B 站登录账号和有效状态；
- 发起独立扫码登录；
- 高级方式导入当前登录态；
- “同步当前主播到云端”开关；
- 已启用云端采集的主播列表；
- 默认 30 天及服务器实际保留策略；
- 最近连接、最近成功采集和最近同步时间；
- 登录失效、连接故障和数据缺口提示；
- 立即同步；
- 停止采集及删除历史入口。

详细直播事件仍在回看档案中展示。设置页不实现第二套事件浏览器。

## 十八、错误与恢复

### 18.1 服务重启

1. 恢复启用房间清单；
2. 验证 B 站登录态；
3. 将上次运行遗留的记录状态收口为已停止，未经新证据确认的进行中场次设为状态未知，已确认结束者保持结束；
4. 查询房间当前直播状态；
5. 核对真实房间号及标准化平台开播时间，按第十节规则续接、创建新场或暂存待确认归属；恢复后的记录状态立即持久化，不等待下一条普通事件；
6. 已结束但未捕获下播则标记结束时间未确认，保存发现已下播时间用于保留期计算；
7. 从最后持久化的采集进度和存活检查到恢复之间记录疑似缺口，已确认的停机范围单独记录。

### 18.2 数据库写入失败

- 使用有界待写队列和批量提交；
- 写入失败时保留当前批次并重试；
- 队列不能随故障时间无限增长；
- 数据库恢复且内存故障记录仍在时，先提交已知丢弃范围，再允许发布越过该范围的同步进度；
- 数据库故障后进程崩溃时，以最后持久化进度到恢复之间作为疑似缺口，不承诺精确知道丢失条数或起止时刻；
- 故障期间发布写入异常状态，存在未提交或结果待确认的批次时不能判完整；
- 排队数据全部成功提交且采集连续时，不因这次暂时写入失败新增不完整结论；确认丢弃、队列溢出或直播期间实际采集中断后记录缺口并标记不完整，恢复后仍保留已确认缺口；
- 单次数据库故障不应同步阻塞所有 WebSocket 读循环。

队列大小、批量大小和提交间隔由真实负载测试确定。

每个房间定期持久化连接存活检查，即使房间没有业务事件也更新；业务批次同时提交采集进度。首次建立连接先写入运行区间，异常退出后依据未关闭区间和已提交进度恢复质量信息。第一版不承诺数据库故障叠加进程崩溃时零丢失，也不增加磁盘暂存队列。

### 18.3 协议与 API 版本

- API 使用显式主版本 `/api/v1`；
- 客户端绑定时交换服务版本、API 版本和共享协议版本；
- API 主版本不兼容时拒绝同步并明确提示升级哪一端；
- 新增命令或字段保持向后兼容；
- 未知字段和未知命令原样保留；
- 原始数据格式保持稳定，业务语义升级不要求服务端全量迁移。

## 十九、验证与验收

每项检查都对应一个明确失败和后续修复方向。

### 19.1 本地与云端连接一致性

同一账号、同一房间、同一时间运行 BB 和 EventFetcher：

- 比较两端收到的命令序列；
- 检查是否存在一端系统性缺失的命令；
- 检查 JSON 和 protobuf 解码结果；
- 检查心跳、超时和短时重连行为；
- 重连后查询最新房间状态；旧请求不得覆盖较新的 LIVE/PREPARING 证据，查询失败不得发布缓存中的旧直播状态。

相同保存样本的解码和连接事件测试必须一致。两条真实连接的上游下发可能不同，现场差异先对照两端原始记录定位是上游分发、网络接收还是解析问题；只有证据指向共享代码时才修改连接或解码层。

### 19.2 断线恢复

直播中人为中断 EventFetcher 网络，应满足：

- 产生明确断线区间；
- 同一开播周期重连后继续原场次，跨开播周期则分场；
- 服务端序号继续递增；
- 场次标记不完整；
- 不把断线期间空白解释为没有事件。

### 19.3 服务重启

直播中重启服务，应满足：

- 恢复同一房间；同一开播周期恢复原场次，停机期间下播再开播必须分场，证据不足时归属待确认；
- 创建新的连接区间；
- 记录停机缺口；
- 不制造重复场次；恢复状态立即持久化，不依赖新弹幕到达；
- 重启前已提交事件仍可查询。

### 19.4 断点同步

让 BB 同步部分页面后退出，应满足：

- 重启后只请求剩余范围；
- SQLite 写入成功后才推进游标；
- 重复请求同一页不生成重复档案事件；
- 云端原始事件与本地标准事件保留来源关联。

### 19.5 登录失效

使 B 站凭证失效，应满足：

- 确认失效后暂停采集；验证请求超时单独显示验证暂不可用；
- BB 明确提示重新登录；
- 已保存历史不受影响；
- 重新扫码后恢复采集；
- 中间缺口仍然存在。

### 19.6 协议演进

使用保留期内的真实原始事件运行新版 adapter，应满足：

- 新命令和新增字段可以重新解析；
- 旧云端数据不要求迁移为新版完整标准 JSON；
- 未识别事件没有在采集阶段丢失；
- protobuf 可以从原始编码载荷重新解码；
- `DANMU_MSG` 的自动发送标记、手机号验证字段和 `SEND_GIFT_V2` 礼物块的支付字段可从原始记录重新解析；缺失字段保持未知，支付不以礼物展示价值代替；
- 客户端关闭自动弹幕或未验证手机号弹幕的显示后，对应原始记录仍完整保存并可同步；
- 天选和红包保留实际收到的中奖名单及资格字段，不按奖品数量推算未收到的中奖者；
- 重复解析保持事件时间和来源身份稳定，不使用重放当刻时间；
- 云端原始记录过期后明确返回不可重解析，本地已有标准事件仍正常浏览。

### 19.7 直播封面

在一场直播中更换封面，应满足：

- 保存每个实际捕获到的封面版本；
- 记录发现区间及时间来源；上游没有提供变更时刻时不伪造准确生效时间；
- 远端 URL 失效后仍可读取已保存文件；
- 场次到期删除时同步清理其封面文件；
- 文件获取失败不阻塞事件采集，并在场次资料中显示缺失。

### 19.8 同步与保留边界

- 小序号批次失败时，大序号批次不能提前发布到已提交进度；恢复后客户端不会越过迟到记录。
- SQLite 事务失败时事件和游标一起回滚；重试不重复写入。
- 没有新增事件但收到下播、封面或归属修正时，元数据修订仍能同步到客户端。
- 未开播期间的礼物和互动可按房间同步，不能因场次为空遗漏。
- 礼物配置变化后，用旧快照解析旧事件，资源缺失与正文丢失分开报告。
- 漏掉下播的场次在确认房间已结束后仍会正常到期，不无限积累。
- 数据库暂时失败后全部排队数据成功提交，记录故障与恢复结果，不凭失败次数判定不完整；尚有待写批次时不能判完整。
- 确认丢弃或队列溢出后保持不完整；数据库故障后进程崩溃，重启后保留疑似缺口及依据，不显示无依据的精确丢失数量。
- 平台开播时间已知但中途加入时，保留开播时间并记录漏采开头；单纯缺少开播时间时保持待确认。
- 同房间开播时间相同但 live_key 不同仍按时间核对同场；仅 key 相同而开播时间不同或缺失时不得据此合并。
- 多房间配置快照独立关联；历史解析跨分页保持上下文，不读取当前实时房间缓存。
- 头像请求延迟、失败或异步回调次序变化不改变原始接收时间与房间序号，不阻塞原始记录写入；未保存的 HTTP 补取结果不被当作原始命令中的历史资料。
- 同步历史礼物、醒目留言和大航海等事件只更新档案，不触发语音、特效、副窗口实时列表或固定卡片，也不改变当前卡片的停留时间。

## 二十、实施分解方向

客户端基线已具备 SQLite 档案、三维场次状态、本地档案包导入导出及封面 URL 保存。服务端原始采集和云端同步按以下阶段实施：

1. 建立 `bb-event-fetcher` 独立私有项目及协议包版本依赖，提取共享协议能力并证明不改变客户端当前连接行为；
2. 建立 EventFetcher 服务骨架、PostgreSQL 和健康接口；
3. 完成 B 站扫码登录及凭证保存；
4. 完成单房间原始采集和数据库写入；
5. 增加持续多房间调度、场次证据匹配、配置快照和质量记录；
6. 增加封面快照和保留期清理；
7. 完成同步 API；
8. 在 BB 中实现服务器绑定和房间管理；
9. 在现有客户端 SQLite 档案上增加云端来源记录、同步游标、解析版本和跨源场次关联，实现原始事件同步、可重复历史解析、持久化去重及档案合并；
10. 完成断线、重启、登录失效和协议升级验收。

每个阶段开始前都应有对应实现计划和验证标准，不能在尚未证明共享连接行为一致时同时重写本地连接与服务端采集。

## 二十一、已知限制

- 登录态不能保证 B 站服务端一定向该账号下发所有理论事件；
- EventFetcher 无法补回自身断线、停机或登录失效期间未收到的普通实时事件；
- B 站协议和接口没有正式稳定契约，需要通过真实原始样本持续维护；
- 第一版不保存封面以外的媒体文件，远端头像、表情、礼物图和特效资源未来可能失效；
- 默认 30 天意味着超过保留期且未同步到本地的数据无法从 EventFetcher 恢复；
- 原始数据到期后不保证已同步本地档案还能重新解析；本地无需永久保存原文；
- 没有可靠业务标识的事件不能保证跨本地与云端完全自动去重；
- 没有充分开播证据时可能保留待确认场次归属，封面轮询也只能记录发现时间；
- 每个节点第一版面向个人少量房间，不承诺公共平台规模。
